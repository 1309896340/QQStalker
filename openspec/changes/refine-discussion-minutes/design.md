## Context

讨论纪要能力已在变更 `add-portrait-discussion-minutes` 中实现（未归档）：`discussion_analysis.py` 负责议题识别、归并、逐题纪要与热度数据，`analyze_transcript.py` 负责组装报告 Markdown 与 HTML 组装脚本，`render_html_png.py` 等待图表就绪后截图。本变更只调整呈现层与纪要文风，不动议题识别、归并与并发机制。动机关见 proposal.md 的 Why。

关键现状：

- `DiscussionReport.to_markdown()` 生成 `## 讨论纪要`、`### 讨论热度` 小节（含 Markdown 表格）与逐议题小节。
- HTML 组装脚本按 H2 文本 `讨论纪要` 定位栏目，把 `### 讨论热度` 标题与表格塞进 `.discussion-fallback`，图表成功时隐藏回退区。
- `render_html_png.wait_for_document_resources` 依赖 `window.__qqstalkerDiscussionChartState` 的 `ready/failed/not-needed` 状态，CDN 超时兜底时隐藏 `.discussion-chart` 容器（注释提到"保留表格回退"）。
- 纪要提示词 `_minutes_instruction` 强制按时间顺序、每句归属发言者与评价行动。

## Goals / Non-Goals

**Goals:**

- 栏目 H2 标题在 Markdown、HTML、PNG 三种表示中统一改为"纪要"。
- 彻底移除热度表格（Markdown 与 HTML 回退），图表失败时栏目只留文字纪要。
- 纪要文风改为主题式归纳，并以 300 字硬上限 + 200 字软引导控制篇幅。
- 纪要人名加粗；HTML/PNG 中按成员确定性着色（同人同色、异人异色）。

**Non-Goals:**

- 不新增环境变量或外部依赖；不改议题区间校验、归并算法、并发与预算机制。
- 不改动群像速览、用户画像、语录精选的人名呈现（高亮仅限纪要栏目）。
- 不追求跨报告的颜色稳定（同人同色只保证单份报告内一致）。

## Decisions

### 1. 标题改动点：报告内容层，控制台文案不动

`## 讨论纪要` 出现在 `discussion_analysis.to_markdown`（正常与空议题降级）、`analyze_transcript` 的专题失败降级文案、HTML 组装脚本的 H2 查找键。三处同步改为 `纪要`；HTML 查找键与生成端必须同一字符串，沿用"精确匹配 textContent.trim()"的现有方式。控制台进度提示（"正在生成讨论纪要"、"讨论纪要（第 N 次请求）"）不是报告内容，保持不变。

备选：把 H2 查找键改成 `startsWith("纪要")` 之类的模糊匹配——被否决，精确匹配更不易误吞相邻栏目。

### 2. 表格彻底移除，图表容器改为插入栏目顶部

- `to_markdown()` 不再输出 `### 讨论热度` 小节与表格行；`chart_payload()` 保持不变，仍作为唯一的热度数据通道。
- HTML 组装：Markdown 里没有 `### 讨论热度` 标题后，现有"heatHeading 前插图表容器 + fallback 区"逻辑成为死代码，整体删除；`.discussion-chart` 容器改为插入到 discussion 区块顶部（第一个议题 H3 之前）。ECharts 初始化、`ready/failed` 状态标记逻辑保留。
- 图表失败时组装脚本对容器 `hidden = true`（`render_html_png` 的 CDN 超时兜底已有同样行为），PNG 中不出现空白框；`render_html_png` 中"保留表格回退"的注释同步更新。
- 备选：保留 Markdown 表格仅去掉 HTML 回退——用户已明确选择彻底移除，避免同一数据在 .md 与 PNG 中以两种形态重复。

### 3. 纪要文风：提示词改主题式归纳，字数用"重试一次 + 确定性截断"双保险

- `_minutes_instruction`（partial 与 merge 两个变体）重写为：围绕核心观点、关键分歧与讨论结果组织成段；合并同类发言，省略寒暄、重复与无关细节；核心观点与分歧归属到具体发言者；仅在 @、引用、点名或语义明确的连续问答有直接证据时写认同/否认；目标 200~300 字。删除"按消息时间顺序呈现"的强制句（这是流水账的直接来源）。分段纪要（partial）沿用同一文风要求，使归并输入已经是压缩形态。
- 上限执行：`normalize_minutes` 在现有结构校验后增加长度校验，`len(段落) > MAX_MINUTES_CHARACTERS`（常量 300）时抛 `RuntimeError`，借 `_validated_request` 的既有机制自动重试一次；重试仍超限时不再让整个议题失败，而是 `summarize_topic` 捕获后做最后一次原始请求，对其输出做句子边界截断（保留到不超过 300 字的最后一个句号/叹号/问号，超长单句在 300 字处硬切）。保证任何情况下最终纪要 ≤ 300 字。
- 下限：不做校验，仅提示词引导；提示词明确"内容不足时如实缩短，不得虚构"。
- 备选：纯确定性截断（不重试）——实现最简，但模型一次压缩失败就接受截断文本，核心内容可能被切掉；纯重试（超限即降级整栏）——把字数问题放大成整栏失败，得不偿失。

### 4. 无实质内容议题的排除：分段判定、代码继承、展示前过滤

- **判定时机与方式**：闲聊与否是语义判断，确定性启发式（消息长度、占比）无法可靠区分，因此在分段提炼提示词（`SEGMENT_PROMPT`）中要求模型在输出议题区间的同时给出 `substantive` 布尔字段，判定标准写入提示词：以寒暄闲聊、表情包斗图、截图交流或无明确主题的重复刷屏为主、缺少可总结观点或信息的区间为无实质内容。`parse_segment_response` 按既有严格风格校验该字段存在且为布尔值，缺失或非法走既有的自动重试一次路径；区间完整覆盖的既有约束不变（闲聊区间仍需覆盖消息，只是被标记）。
- **归并继承**：`MERGE_PROMPT` 不增加字段；`TopicCandidate` 携带 `substantive` 标记，归并议题按"任一候选实质即实质"在代码中确定性继承（OR）。若模型在归并时把一段闲聊误并入实质议题，只影响该议题的消息计数，不会把实质议题整体挤掉；反之闲聊候选之间互相归并后仍为无实质。
- **过滤时机**：`analyze_discussion_minutes` 在排序取 top-k 之前先过滤掉无实质候选，纪要撰写请求只为入选的实质议题发出（省请求）；被排除议题的消息不归属到其他议题，热度图仍只由展示议题构成，与现状一致。
- **全无实质的退化**：所有议题均无实质时复用现有空报告路径（"纪要暂无可总结的有效讨论议题"）。
- 备选：独立的一次"实质性与否"分类请求——额外请求成本与失败面，且分段阶段模型已通读全文，判定最自然；确定性启发式——无法识别"看起来字很多但没有内容"的闲聊。

### 5. 人名高亮：Python 侧按可信名单加粗，JS 侧按注入映射着色

- **名单来源**：参与讨论分析的有效消息成员（`filter_discussion_messages` 产物的 member 集合）。这是从导出记录直接得到的可信数据，与模型输出无关。
- **加粗（Markdown 生成端）**：报告定稿后（议题纪要与参与者行均已就绪），按成员名单对每段纪要文本与"主要参与者"行做最长匹配优先的姓名包裹（`**姓名**`）。在 `DiscussionReport` 层实现（接收成员名单），`normalize_minutes` 同步剥离模型输出中的行内强调标记（`**`/`__`），避免与包裹结果叠加成 `****`。Markdown 阅读器由此获得加粗；HTML 转换后对应为 `<strong>`。
- **配色（确定性、报告内唯一）**：收集纪要文本中实际出现的成员姓名，按首次出现顺序编号，用黄金角散列分配色相（`hsl((index × 137.508°) mod 360, …)`，固定饱和度/亮度，保证可读）。首现顺序保证"同一成员在任何议题中同色"，黄金角间隔保证"不同成员色相互不相同"（任意数量成员都不重色）。以"成员名→颜色"映射随 `chart_payload` 同路注入渲染层，作为受信任结构化数据（与现有图表数据同等级，非模型输出）。
- **着色（HTML 组装端）**：组装脚本遍历 discussion 区块内的 `<strong>` 元素，仅当其 `textContent` 精确命中注入映射时设置 `color`（class/内联样式），其余 strong（如"主要参与者"标签）不动。不使用 innerHTML 拼接模型文本，姓名高亮不引入注入面。
- 备选：纯 JS 在文本节点里做姓名匹配着色——匹配逻辑进浏览器、难以单测，且与 Python 侧加粗匹配规则可能不一致；按成员哈希直接定色——不同成员可能撞色，违背"异人异色"。

### 6. 高区分度配色与姓名背景样式

- **议题（面积图）**：现有 `COLORS` 仅 5 个固定色且按 `position % 5` 循环复用，议题数超过 5 时面积与图例必然撞色——这正是"高区分度"要修的实际缺陷。方案：替换为精选的色盲友好高区分度定性调色板（Okabe-Ito 系，去掉近黑色），议题数不超过调色板容量时直接取用；超出容量时按索引以黄金角色相确定性生成补足（固定饱和度/亮度），任意议题数下颜色互不重复。面积填充沿用现有半透明 `areaStyle`，色相差异在半透明叠加下仍可辨。备选：全部用黄金角生成——少量议题时不如人工挑选的组合悦目；把固定调色板扩到 10+ 色——靠后颜色的人工区分度难以保证。
- **姓名**：决策 5 的黄金角配色已保证报告内异人异色；本决策调整其呈现参数与背景样式。前景文字取同色相深色（保证对比度可读），背景取同一色相的高亮度低饱和浅色（类似荧光笔淡染、无边框），再加粗。前景/背景同色相意味着不引入新色相——区分维度仍是色相本身，背景只提供"块状扫描点"，满足"用背景色辅助区分"的同时把杂乱控制在最低。
- **背景样式的取舍**（用户明确要求权衡）：(a) 仅彩色文字——版面最干净，但黑白正文中扫读定位姓名慢；(b) 彩色文字 + 边框/描边的完整 chip 样式——最醒目，但纪要提到多人时版面花哨杂乱；(c) 采用同色系浅背景、无边框——折中：有背景提供扫描锚点，低饱和保证整页以白底为主。背景只应用于纪要段落与参与者行中命中的姓名，标题、时间范围等其余元素不受影响。
- **数据通道**：注入渲染层的受信映射从"成员名→颜色"扩展为"成员名→{文字色, 背景色}"两个值，由 Python 侧一次性生成，JS 仍按精确命中应用，不做二次计算。

### 7. 归档顺序

本变更的 MODIFIED delta 以 `add-portrait-discussion-minutes` 归档后的主规格为基准。先归档原变更，再归档本变更；`openspec validate` 在原变更归档前可能提示主规格中找不到被修改的需求，属预期。

## Risks / Trade-offs

- [成员名与普通词汇重合（如成员名"哈哈"）导致误加粗] → 接受该权衡：名单来自真实群成员，误标范围仅限纪要段落；不做语义判断，保持确定性。
- [模型未按原文写姓名（简称/错字）导致漏高亮] → 提示词要求使用消息中的原始成员名；漏匹配只影响视觉呈现，不影响内容。
- [Markdown 中 `**姓名**` 紧邻标点或汉字的渲染兼容性] → 常见 CommonMark 实现（marked）对 CJK 相邻强调表现稳定；渲染测试覆盖中文标点相邻用例。
- [黄金角色相在极少数情况下仍可能视觉接近] → 议题色先取精选高区分度调色板、超容量才用黄金角补足；姓名色背景与文字同色相、低饱和，即使两色相接近，加粗与浅背景仍保持可辨识；均为确定性输出，可在测试中断言互异。
- [超限截断可能切掉段尾内容] → 先经一次模型重试压缩，截断只作兜底；截断按句子边界，避免半句。
- [模型对边界议题（有互动但价值低）判定过严或过宽] → 判定标准写入分段提示词并保持二元简单判定；过宽时最多混入个别闲聊议题，过严时报告议题变少但不虚构，均不阻断报告生成。
- [归档顺序依赖] → 在 proposal 与本设计中显式记录；若先归档本变更会导致 MODIFIED 落空，验证时应留意。

## Migration Plan

纯呈现层与提示词改动，无数据迁移。实现完成后按 tasks.md 回归：unittest 相关模块、`uv run pyright`、`uv run python -m compileall -q src`；归档时先 `add-portrait-discussion-minutes` 后本变更。回滚即还原两个文件的呈现逻辑，无持久化影响。
