## Context

一次画像生成涉及几十到上百次大模型请求，全部经由 `request_portraits` 发起；请求之间的唯一组织方式是函数调用，没有任何持久化。报告生成中任何一处失败（实测：仅两个议题纪要失败）后重跑都要求全价重跑。输出目录 `analysis/` 已被 git 忽略，缓存文件不会进入版本库。

## Goals / Non-Goals

**Goals:**

- 重跑时成功请求零成本复用，失败请求自动重试。
- 缓存对请求方透明：调用方（画像/纪要/语录/总览）不感知缓存存在。

**Non-Goals:**

- 不做缓存过期/淘汰策略（聊天记录与 prompt 不可变，旧缓存不会变陈旧；磁盘占用由用户手动清理）。
- 不缓存校验通过与否的状态——缓存存原始响应，校验仍在每次读取后执行。
- 不改变重试次数、并发数、输入预算等既有行为。

## Decisions

- **进程级安装而非逐层传参。** 在入口解析参数后调用 `llm_cache.install(cache)` 安装进程级缓存实例，`request_portraits` 内部查询；`--no-cache` 即不安装。备选"为 `request_portraits` 的全部调用点显式传 cache 参数"改动面大且容易漏；进程级单例与现有 `reporter` 的使用方式风险相当，且缓存本质是运行环境配置而非业务参数。
- **键 = sha256(阶段标签 + 模型 + 请求参数 + prompt)。** 请求参数取影响响应的字段（max_tokens、timeout 不影响内容不参与；max_tokens 影响截断行为故参与）。`finish_reason` 随响应一起缓存，命中后下游的截断交互/审查处理逻辑照常运行，与网络请求行为完全一致。
- **成功即缓存（含后续会被判校验失败的响应）。** 缓存的是模型原始输出；校验在读取后照常执行。这样重跑时校验失败重试用的是同一份缓存输出，行为可复现、便于调试重试逻辑；若每次重跑都重新请求，反而无法稳定复现失败。
- **原子写入。** 先写 `<key>.tmp` 再 `os.replace`，避免并发或中断留下半个 JSON；读取时解析失败视为未命中并删除损坏文件。

## Risks / Trade-offs

- [缓存文件含聊天记录内容的响应] → 位于 git 忽略的输出目录；`--no-cache` 可彻底关闭。
- [prompt 完全相同但用户期望重新生成] → 提供开关；且模型本就非确定性，复用旧响应与重新请求无对错之分。
- [进程级安装导致测试互相污染] → 安装接口提供卸载/清理，测试 teardown 复位。

## Migration Plan

单次代码变更，无数据迁移；缓存从启用之日起逐步累积。回滚即还原提交（缓存目录可整体删除）。
