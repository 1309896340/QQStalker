# QQ 群员画像全自动化方案分析

## 结论摘要

项目已经具备可靠的“离线批量生成”骨架：导入会按消息外部 ID 去重，`generate_portrait` 能在一次命令中完成消息导出、模型分析和图片渲染。但它还不是端到端自动化产品：聊天记录获得、任务调度、失败恢复、结果分页和群内分发，仍主要依赖人工。

推荐把目标定义为两层，而不是把所有问题塞进一个命令：

1. **本地一键批处理（近期）**：用户把 QQChatExporter 导出放入固定收件目录后，程序自动识别新导出、导入增量消息、生成群分享卡组，并给出可直接上传的结果目录。
2. **持续自动化（后续）**：只有在有合规、稳定的持续消息来源时，才接入 NapCat 的事件或历史消息能力，由调度器按周期生成增量报告。

第一层不需要改变 QQ 数据来源，也足以消除绝大部分重复操作；第二层不能仅靠现有 QQChatExporter 文件实现，因为导出动作本身仍在系统外部。

## 当前链路与已具备能力

当前可执行链路如下：

```text
QQChatExporter 导出目录
        |
        v
src.import_export
        |
        v
PostgreSQL（消息、成员、群名片、@、资源）
        |
        v
src.export_markdown
        |
        v
src.analyze_transcript（LLM）
        |
        v
HTML 报告
        |
        v
src.render_html_png
        |
        v
PNG 分片 / 横向拼图
```

`src.generate_portrait` 已将中间三步串联：按日期和群名查询数据库、临时导出 Markdown、调用 LLM、保留 HTML 并渲染 PNG。导入层也有良好基础：`messages` 对 `(chat_id, external_id)` 有唯一约束，同一份或重叠导出的新旧消息可以安全跳过；`ImportBatch` 记录了导入文件修订。

因此，后续设计不应推倒数据库或重新做分析引擎，应围绕已有的“可重复导入”和“一键生成”能力补齐输入、编排和输出。

## 主要不便与根因

| 环节 | 现状 | 不便 / 风险 | 根因 |
| --- | --- | --- | --- |
| 数据采集 | 手动用 QQChatExporter 导出，再手动运行导入 | 无法自动发现新消息；容易忘记导出范围 | 外部数据源没有接入点或收件约定 |
| 运行准备 | 依赖 Docker PostgreSQL、`.env`、Playwright 浏览器 | 初次配置复杂；错误往往在运行到中间环节才暴露 | 缺少环境自检与统一入口 |
| 任务选择 | 命令要求输入日期、群名、输出目录及多个分析参数 | 高频使用时重复输入，容易选错群或日期 | 缺少预设、默认范围和任务配置 |
| 分析输入 | 先生成完整 Markdown，再从标题和引用中解析成员 | 文本格式同时承担展示和机器传输职责，耦合且脆弱 | 没有面向分析的结构化消息 DTO |
| 分析质量与成本 | 默认尝试为所有可识别成员画像 | 大群耗时、费用和输出长度会随成员数线性增长；低活跃成员常缺证据 | 没有报告级的成员准入、摘要与缓存策略 |
| 上下文 | 现有按成员聚合会弱化原始时间顺序 | 对“回应、协作、分歧、群内角色”的判断证据不足 | 对话窗口尚未进入分析输入；已有提案已识别此问题 |
| 结果生成 | HTML 再以 300 DPI、最多 30000px 高的 PNG 截图 | 偏打印用途；像素切分会切断成员内容，图片体积也不受群聊约束 | 渲染器按物理页面和高度切图，而非报告语义分页 |
| 分发 | 用户自行判断传什么、上传多少张 | QQ 禁文件的群无法发 HTML；大图上传失败、横向拼图难在手机阅读 | 没有“群分享版”产物与文件大小预算 |
| 可靠性 | 网络 / LLM 出错后以异常结束 | 不清楚哪一批成员已完成；重跑会重新请求模型 | 没有任务状态、阶段产物、重试和模型结果缓存 |

## 自动化目标与非目标

### 推荐目标

- 用户只需完成不可替代的授权或采集动作；其余步骤由单一入口完成。
- 新导出可安全重复投递，已导入消息不重复入库。
- 每次报告有明确的群、时间范围、版本、模型和生成状态，可追溯、可重跑。
- 默认产物是可直接发送 QQ 群的 JPEG 卡组，而 HTML 是完整存档。
- 先产出可读的群级摘要，再按成员按需展开，避免大群一次性制造几十张图。
- 对所有画像保留“仅基于指定聊天记录的模型解读”声明，避免敏感属性推断和事实化表达。

### 非目标

- 不应试图绕过 QQ、群管理员或平台权限来获取消息。
- 不将公开群分享等同于可以公开完整的成员行为档案。
- 不在第一阶段引入 Web 服务、账号体系或 QQ 小程序；这些会将一个本地工具变成需要运维和合规设计的产品。

## 推荐架构

```text
                 +--------------------+
                 | 导出收件目录 /      |
                 | 合规消息连接器      |
                 +----------+---------+
                            |
                            v
+----------------+   +-------------+   +------------------+
| 预检与任务配置 |-->| 增量导入器  |-->| 报告任务记录     |
+----------------+   +------+------+   +--------+---------+
                            |                   |
                            v                   v
                     PostgreSQL           可恢复的阶段状态
                            |
                            v
                     结构化分析准备
                            |
                            v
                 +--------------------+
                 | LLM 分析与结果缓存 |
                 +----------+---------+
                            |
                  +---------+---------+
                  v                   v
          完整 HTML 存档       QQ 分享 JPEG 卡组
```

### 1. 输入层：先统一“新数据如何到达”

近期应采用**固定收件目录 + 文件监听或定时扫描**：约定 QQChatExporter 的输出目录或让用户把导出目录放入 `inbox/`；工具验证 JSON 和 `resources/` 是否完整、计算文件哈希、调用现有导入逻辑，并将已处理项移到按日期归档的目录。导出仍需用户完成，但“找到文件、运行导入、确认重复导入”这些机械步骤消失。

若以后确实需要无人值守，才能评估 NapCat 等合规连接器。连接器应只产出一个稳定、可版本化的内部消息事件格式，不能让下游分析逻辑直接依赖某个 QQ 协议实现。要先确认账号授权、群规则、数据保存期限与访问控制；这些是产品边界，不是纯技术细节。

### 2. 编排层：一个用户入口，多个可恢复阶段

引入 `run` 概念，而不是只依赖一次 CLI 进程：

```text
queued --> importing --> preparing --> analyzing --> rendering --> ready
                         |                 |
                         v                 v
                      failed <---------- retrying
```

每个 run 至少记录：群唯一 ID、时间范围、输入批次、配置快照、模型与提示词版本、阶段状态、开始/结束时间、错误摘要和产物路径。这样可以：

- 在 LLM 第 4 批失败时，只重试未完成成员；
- 复用同一时间范围的统计和已成功的画像；
- 让用户清楚知道“数据已导入但报告尚未完成”还是“已经有可分享图片”；
- 以后无缝挂到 Windows 计划任务，而不需要依赖常驻终端。

第一阶段的入口可以保持 CLI，例如提供“检查收件目录并生成最近 7 天群分享版”的预设。不要一开始上 GUI；待流程稳定后，再决定是否提供极薄的本地界面。

### 3. 分析层：以结构化数据而非展示 Markdown 为边界

数据库中已有消息时间、发送者、群名片、提及和资源元数据。分析前应直接构造结构化对象，例如：

```text
ReportInput
  - chat: id, display_name, period, message_count
  - members: id, display_name, message_count, activity_windows
  - messages: sequence, timestamp, sender_id, text, mentions, reply/context
  - selected_members: ranked and eligibility-filtered
```

Markdown 仍可保留为人工审阅和归档格式，但不再作为 LLM 输入的唯一中间格式。这样能避免依赖正则从展示标题反推成员，也便于精确裁剪输入。

成员画像应采用“统计 + 代表性消息 + 合并的上下文窗口”模式。仓库已有的 `docs/proposals/contextual-member-portrait-analysis.md` 已明确指出：必须保留目标成员发言前后的时间序列，且只在有直接证据时讨论互动或影响。该提案应成为提升画像可信度的优先项。

建议默认报告策略：

- 用最低消息数、活跃度或时间跨度筛掉“证据不足”的成员；
- 先分析 Top N 活跃成员，其他成员只在完整报告或显式开关中生成；
- 为每位成员限制上下文窗口和字符预算，并保留跨时间段代表性；
- 以“输入内容哈希 + 提示词版本 + 模型配置”作为画像缓存键；
- 模型输出先校验成员覆盖、字段结构和敏感推断约束，再进入渲染。

### 4. 输出层：从长截图改为语义化的群分享卡组

现有 `render_html_png` 的默认参数为 300 DPI、210mm 宽、单图最多 30000 物理像素高。这是印刷级设定，不是群聊图片设定。高度分片只根据像素位置，不知道成员卡、标题或引用的边界；`--stitch-horizontal` 虽减少文件数量，但会增大横向尺寸，在手机上尤其难读。

应将输出拆为两个产品：

| 产物 | 读者 | 内容 | 建议格式 |
| --- | --- | --- | --- |
| 完整存档版 | 发起人 / 审阅者 | 全成员、完整免责声明、配置与生成时间 | HTML；后续可选 PDF |
| 群分享版 | QQ 群成员 | 总览、重点成员卡、精选语录、简短声明 | 多张 JPEG |

分享版先按内容分页，再渲染与压缩，而不是先生成长图再切。建议的卡片序列是：

```text
01 群聊总览（范围、活跃度、话题、声明）
02-0N 成员画像（每张 3-5 个完整成员卡）
最后 语录精选 / 生成说明
```

建议将宽度固定为 1080px，单张采用 4:5 或受控最大高度（例如 1350-1800px），JPEG 质量 80-88，并设置文件体积上限作为渲染验收条件。超过预算时，应降低质量或缩短该卡内容；绝不能在成员卡中间按像素硬切。每张都应带页码、群名和日期，使转发或图片乱序时仍可理解。

QQ 的具体上传限制会随客户端和群设置变化，因此不能把某个未验证的硬编码数值当作真相。实现时应将单张最大字节数设计为可配置的保守预算，并用真实目标群的样本验证后再调整默认值。

## 方案比较

| 方案 | 自动化程度 | 复杂度 | 对现有代码的复用 | 推荐度 |
| --- | --- | --- | --- | --- |
| 继续手动运行现有 CLI | 低 | 低 | 高 | 不建议长期维持 |
| 收件目录监听 + 一键 run + JPEG 卡组 | 高（采集后） | 中 | 很高 | **近期首选** |
| Windows 计划任务定时跑固定群与周期 | 高（采集后） | 中 | 高 | 适合第二小步 |
| NapCat 实时/历史消息连接器 | 端到端潜力最高 | 高 | 中 | 仅在合规需求明确后 |
| 自建网页 / 小程序发布报告 | 分发体验好 | 高 | 低到中 | 不作为当前问题的首选 |

## 分阶段实施路线

### 阶段 A：把现有离线流程变成稳定的一键任务

目标：不改变数据源，通过一个命令完成预检、导入、生成和结果摘要。

- 为常用群和周期建立非敏感的任务配置（例如群 ID、默认窗口、Top N、报告版式）。
- 增加环境预检：数据库连通性、`.env` 必要项、Playwright 浏览器、输出目录可写性。
- 增加收件目录扫描和导入结果摘要；复用现有外部 ID 去重。
- 将每次运行的输入、参数和产物写入 run 记录；失败给出可操作提示。

验收：用户把有效导出放入约定目录后，只需一次命令即可得到完整 HTML 和待上传的分享图目录。

### 阶段 B：提升画像可靠性与可恢复性

目标：让输出更可信，且故障不浪费已完成的模型调用。

- 按已有上下文分析提案，改用结构化消息和合并窗口。
- 增加成员筛选、分析缓存、模型输出校验和逐成员重试。
- 将生成结果与模型、提示词和输入快照关联，支持“保持原配置重跑”。

验收：中途中断后可以恢复；同一输入不重复请求模型；成员画像中的互动结论能追溯到可见上下文。

### 阶段 C：交付群分享版

目标：结果不依赖文件上传，可稳定以图片发送。

- 将报告数据和渲染模板分离；先做卡片级分页器。
- 输出 JPEG 卡组、封面总览、页码和简短声明；保留 HTML 存档。
- 添加尺寸、单张字节数、卡片完整性等自动检查，并以真实 QQ 群做人工验收。

验收：任何一张图都可独立阅读；图片不在成员卡中间断开；目标群可成功上传全部卡片。

### 阶段 D：可选的持续运行

目标：减少“记得运行”的人工环节。

- 先以 Windows 计划任务定期扫描收件目录、生成最近周期报告。
- 只有确定需要真正无人值守并已完成授权与隐私设计时，再调研消息连接器。

验收：重复运行幂等；无新数据时安静退出；有新数据时只处理增量并留下结果状态。

## 风险与防护

| 风险 | 防护措施 |
| --- | --- |
| 群成员画像被当作事实或引起冲突 | 默认使用审慎措辞；显示时间范围和证据不足；禁止敏感属性、心理诊断和现实关系推断 |
| 聊天内容、API Key 或报告泄漏 | `.env` 不入库不输出；产物目录按本地私有处理；日志不记录原文和密钥；设置保留/清理周期 |
| 大群导致成本和等待不可控 | 成员准入、Top N、输入预算、缓存、逐成员重试和成本预估 |
| 重叠导出或重复调度 | 复用消息唯一键；run 以群和时间范围加配置指纹去重或显式复用 |
| QQ 图片上传行为变化 | 输出预算可配置；在真实目标客户端回归验证；始终保留原始 HTML 存档 |
| 自动采集触碰平台或群管理边界 | 只采用用户有权使用的数据来源；在连接器阶段单独评估权限、通知和数据最小化 |

## 推荐的下一项决策

先确认“自动化”的边界：是否接受用户仍需定期用 QQChatExporter 导出并放入固定目录。若接受，应直接从阶段 A 与阶段 C 开始；它们能最大程度复用现有工程，也能立刻解决群内分享困难。若必须完全无人值守，则应先做数据来源与授权的专项调研，再讨论 NapCat 连接器，避免在输出层投入后仍卡在数据采集入口。
