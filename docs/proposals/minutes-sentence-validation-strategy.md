# 讨论纪要句读校验策略待改进

## 背景

在改进纪要失败降级方案（openspec 变更 `improve-minutes-fallback`）时，从 `analysis/.llm-cache` 取证了纪要校验被拒的原始响应，结论如下。

## 取证结论

缓存中被拒的两条议题纪要（对应报告里"影视相关日常分享与讨论"与"RTS及相关游戏讨论"两个降级议题）均为 **714 / 778 字、全文只有结尾一个句号**的长句：模型全程用逗号、分号连接，仅结尾落一个句号。`_normalize_minutes_text` 以"句末标点（。！？!?）≥ 2"判定多句自然段，因此拒绝。

排查中还发现缓存里大量 JSON 响应、拒答文本（"抱歉，我无法回答"）与画像内容——这些是其他阶段（分段识别、归并、画像）的正常响应，与纪要校验无关。

## 已修复（同变更内）

`_bounded_minutes` 的最后兜底 `truncate_minutes(_normalize_minutes_text(...))` 中，多句校验先于截断抛错，导致重写穷尽后的保底截断永远不可达，所有顽固失败都掉到发言摘录兜底。已修复：最后尝试对"够长（≥60 字）且非 JSON 开头"的散文段落只做清洗 + 句子边界截断后保留；拒答与 JSON 垃圾仍向上抛错。

## 待改进（策略级，另开变更）

1. **生成侧治理优先**：`_minutes_instruction` 只说"由多个简明句子组成的自然段"，模型仍倾向逗号连缀。可考虑在指令中显式要求"每个分句必须以句号/问号/叹号结束"，从源头减少长句拒收。
2. **校验侧容忍度**：可评估把分号（；）、句读节奏纳入句子判定，或对"单句但超过 N 字"的响应走一次定向重写（"请按句号切分"）而不是整体拒绝。
3. **缓存信息量**：`LlmResponseCache` 目前只存 `response`/`finish_reason`，不存 prompt 与 stage 标签，排查时只能靠内容形状辨认阶段。可考虑补充 stage 元数据便于取证。
