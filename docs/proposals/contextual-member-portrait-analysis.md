# 提案：基于对话上下文的群员画像分析

## 背景

当前 `src/analyze_transcript.py` 会先按群名片聚合消息，再将若干成员的全部消息放入同一批请求中交给大模型。这种方式能够分析发言频率、语言风格和常见话题，但原始群聊的时间顺序会丢失：模型无法稳定识别一条消息在回应谁、某次互动的来龙去脉，或成员在具体讨论中的角色。

## 目标

在保留现有“每位群员均输出一份画像”和分批请求机制的基础上，为每名目标成员提供其发言附近的原始群聊上下文。模型应能依据可见的对话往来，更可靠地描述互动风格、群内角色和直接可见的关系与影响。

## 非目标

- 不推断聊天记录之外的现实关系、身份或敏感属性。
- 不要求为每一条消息重复发送整份群聊记录。
- 不改变 Markdown 导出、数据库结构或 HTML 渲染流程。

## 建议方案

1. 保留按时间顺序解析导出的消息记录，生成带有时间、发言者、内容和消息序号的标准消息列表。
2. 仍按成员汇总其消息，用于计算活跃度、代表性发言和分批调度。
3. 对每名成员选取有限数量的代表性发言；针对每条发言，从原始消息列表中截取其前后固定条数或固定时间窗口内的消息。
4. 合并重叠窗口、按原始时间顺序去重，并为每条上下文消息明确标出发言者与时间。
5. 请求模型时同时提供：
   - 目标成员的消息统计与代表性发言；
   - 该成员的上下文片段；
   - 同批成员清单及既有的完整性输出约束。
6. 在提示词中强调：只有在上下文中存在直接证据时，才能描述“回应”“调侃”“协作”“分歧”等互动；否则应标注为无法判断。

## 可配置项建议

在 `.env.example` 中增加以下可选配置，并给出保守默认值：

- `LLM_CONTEXT_MESSAGES_BEFORE`：目标消息前保留的消息条数，例如 `3`。
- `LLM_CONTEXT_MESSAGES_AFTER`：目标消息后保留的消息条数，例如 `3`。
- `LLM_MAX_CONTEXT_WINDOWS_PER_MEMBER`：每名成员最多选取的上下文窗口数，例如 `12`。
- `LLM_MAX_CONTEXT_CHARACTERS_PER_MEMBER`：每名成员上下文的字符上限，例如 `12000`。

实现时仍应受 `LLM_MAX_INPUT_CHARACTERS` 约束；当上下文超限时，优先保留不同时间段和不同话题下的窗口，而非只截取最早的消息。

## 提示词输出调整

保留当前画像字段，并将“关系与影响”改为更严格的证据要求：

- 说明可直接观察到的互动对象、触发话题和互动类型。
- 将原文可验证的上下文片段作为证据之一。
- 若缺少上下文或证据不足，明确写“无法判断”，不以同批成员同时出现作为互动依据。

## 验收标准

- 同一成员的输入中，至少能看见其代表性发言前后的其他成员消息，且保持原始时间顺序。
- 上下文窗口不会因重叠导致重复消息或超过配置的输入上限。
- 画像仍覆盖全部已识别成员；现有的缺失成员补偿逻辑继续有效。
- 当上下文不足时，工具能正常运行，并在画像中体现证据不足，而非报错或编造互动。
- 使用包含明确问答、引用或 @ 提及的测试记录时，生成结果能引用这些可见互动，且不把无关成员错误关联为互动对象。

## 实施后的验证

为解析与窗口合并逻辑补充单元测试，并执行：

```powershell
uv run pyright
uv run python -m compileall -q src
```

再使用一份脱敏的小型导出记录进行端到端检查，确认请求体大小受限、所有成员都有输出，且 HTML 中能正常展示结果。
